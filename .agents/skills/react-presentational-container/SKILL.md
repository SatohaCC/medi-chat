# Reactの表示とロジックの分離

## 出典と基本原則

[Patterns.dev — Container/Presentational Pattern](https://www.patterns.dev/react/presentational-container-pattern/)

表示コンポーネントは受け取ったpropsを描画し、入力データを変更しない。表示目的のローカル状態は持てる。Containerはデータ取得やアプリケーション状態を扱い、表示へ渡す。custom Hookでもロジックを分離できるため、ラッパーを必須にしない。表示の独立は再利用、見た目の変更、テストを助ける一方、小さなUIでは分割が過剰になり得る。

以下は、この原則を実装・レビューへ適用するための補足指針であり、記事のサンプルコードの再現ではない。

## 構成を選ぶ

まず対象のデータ取得・購読、アプリケーション状態、ユーザー操作、表示用の状態、描画を識別する。既存の呼び出し元、データ取得方式、フレームワークの境界も確認する。

| 構成 | 選ぶ理由 | 注意点 |
|---|---|---|
| propsで受け取る表示 + 薄いContainer | 同じUIを異なるデータ源で使う、独立してプレビューする、外部サービスなしで描画を検証する | 接続側が必要なデータと操作を渡す。スタイルや表示処理まで接続側に集めない |
| custom Hookを呼ぶコンポーネント | 状態と操作を再利用し、接続用ラッパーを増やす利益が少ない | HookがAPIやストアに依存すれば、呼び出し側もその依存を持つ。ロジック抽出と表示の独立性を区別する |
| Hook + Container + 表示 | ロジックの再利用と独立した表示境界の両方が必要 | 各境界に具体的な役割がある場合だけ組み合わせる |
| 分割しない | 責務が単純で、分割しても再利用・理解・検証が改善しない | 小さいコンポーネントにも機械的にContainerを要求しない |

Containerは関数コンポーネントでもよく、クラス化や特定の接尾辞を要求しない。Hookを呼ぶだけで、外部依存のない表示になったとは判断しない。

## 実装の指針

- 表示のpropsには必要なデータと、`onSelect`など操作の意図を示すコールバックを渡す。HTTPクライアントやストア全体を渡す前に、表示が必要とする契約まで絞れるか検討する。
- 展開・選択・フォーカス等の状態は、意味と利用範囲で所有者を決める。表示内で完結するなら表示側、共有・永続化・業務判断に関わるなら適切な上位の所有者へ置く。
- propsや共有データを直接変更せず、操作を所有者へ通知する。単なる表示用の変換だけを理由にHookやContainerを新設しない。
- ロジック抽出だけで取得方式を変えない。既存のサーバー取得・キャッシュ・購読方式を尊重し、記事の例を理由にクラスや素朴なfetch/useEffectへ置き換えない。
- Effectは接続・購読等の外部同期に使い、ユーザー操作で始まる処理はイベントハンドラやコールバックへ置く。
- 非同期処理を変更する場合、loading・empty・error・success、再試行、競合・解除の扱いを既存契約と照合する。Hookの抽出によって二重取得や購読の重複を生まないか確認する。
- 同じcustom Hookの呼び出し同士で状態が共有されるとは仮定しない。共有が必要なら既存の所有者・ストア・キャッシュを確認する。
- このプロジェクトのfrontendを変更するときは、適用されるAGENTS.mdと指定の設計・検証資料に従う。このSkillだけでプロジェクト固有の規約を置き換えない。

## 検証とレビュー

変更した責務に応じ、表示はデータ・状態別の描画と操作通知、ロジックは取得・更新・失敗時の振る舞い、接続部分は操作から画面更新までを確認する。ファイルの分割や命名そのものをテストしない。既存の適切なテストを優先し、プロジェクトの品質ハーネスを使う。

レビューでは混在による具体的な問題と、それを解消する境界を示す。「Containerがない」「Hook化されていない」だけで不具合にしない。変更後は選んだ構成、利益、増える依存・間接参照、実際に検証した範囲を簡潔に説明する。分割の利益がなければ、変更不要と判断してよい。
