# 回答へのユーザー評価：テスト仕様

## 追加仕様：取消と送信中の見た目

2026-10-29のユーザー依頼により、選択済みボタンの再クリックで評価を取り消す。`PUT /api/chat/feedback`の`rating`は必須項目のまま`"up" | "down" | null`を受け付け、nullはLangSmithのfeedback削除を表す。成功応答も同じratingを返す。削除済みの再取消は成功とし、その後の再評価は同じfeedback IDを使う。

取消も楽観的に未選択を表示し、失敗時は直前の評価へ戻して取消操作を再試行できる。送信中は両ボタンを無効化するが透明度は変えない。ブラウザで通信を保留し、両ボタンのopacityが1のままであること、up/downそれぞれの再クリック、取消失敗時の復元と再試行を検証する。

## 対象と契約案

正常に完了した回答へ、認証済みユーザーが👍／👎を付ける。回答・評価者ごとに1件とし、反対の評価への変更と再クリックでの取り消しができる。コメント・再読み込み後の復元・自動学習は対象外。

- RESTの回答とWebSocketの`text_done`へ`feedback_token: string | null`を追加する。評価不能時はnull。エラー・中断イベントには付与しない。
- トークンはサーバー署名、有効期限、認証主体、回答に対応するLangSmith run、評価に必要な接続先識別情報を結び付ける。APIキー・回答本文は含めない。署名は暗号化ではないため秘密情報を載せない。
- `PUT /api/chat/feedback`の入力は`feedback_token`と`rating: "up" | "down" | null`。成功時は200と、受け付けたratingを含むJSONを返す。
- 評価キーは`user_feedback`、upは1、downは0。同一回答・評価者の再送・変更では同じfeedbackを操作する。
- 評価APIは既存の認証、Origin、CSRF検証を使用する。認証切れは401、Origin/CSRFまたはトークンの改ざん・期限切れ・主体不一致は403、不正入力は422、LangSmith未設定・一時障害は503、送信タイムアウトは504を契約案とする。
- フロントは保存確認前に「送信済み」を表示しない。タイムアウト時は保存された可能性もあるため、失敗表示から同じ評価を安全に再送できるようにする。
- 評価は会話履歴へ含めない。評価通信の失敗によって生成処理を失敗させない。

トークンの有効期間・署名鍵の設定方法は実装開始前に既存設定と照合して定める。境界テストは注入した時計で行い、期限の直前は受理、期限ちょうど以後は拒否する。

## Backendのケース

外部通信を除き、実際のDTO・ユースケース・署名処理を使う。SDK通信は境界で置き換え、内部の判定式そのものを期待値に流用しない。

| ID | 入力・条件 | 観測と期待結果 | 層 |
|---|---|---|---|
| B01 | 正常な回答をRESTで取得 | tokenが返り、そのtokenによる評価が当該回答のrunに保存される | Presentation結合 |
| B02 | WSで2回答を完了し、最初を評価 | 各text_doneのtokenが独立し、最初の回答のrunだけへ保存される。request_idをrun_idの代用にしない | Presentation結合 |
| B03 | 生成中断・例外・接続断 | 評価可能な完了tokenを公開しない。次のリクエストへtokenが流用されない | Presentation |
| B04 | LangSmith無効、または評価機能の設定不足 | 正常回答は維持し、tokenはnull。評価APIは503 | Presentation/Infrastructure |
| B05 | 有効tokenでup/down | 対応run、固定キー、1/0が保存先に渡る。ユーザー入力で接続先やキーを変更できない | Application |
| B06 | 同じtoken・ratingを繰り返し送信 | feedbackの観測上の件数は1件。応答喪失後の再送も同じ結果になる | Infrastructure/結合 |
| B07 | up保存後にdown、その後up | 同じfeedbackのscoreが順に変わり、複数の評価として集計されない | Infrastructure/結合 |
| B08 | 同じ評価の同時送信、変更要求の競合 | 重複作成しない。異なるratingの同時要求では処理完了順のいずれか1値が残り、永続値と応答を観測する。順序保証を捏造しない | Infrastructure/結合 |
| B09 | 別回答、別評価者 | 独立したfeedback IDとなる。別ユーザーが元のtokenを送ると403、SDK呼び出し0回 | Application/Presentation |
| B10 | token改ざん・不正形式・期限境界 | 403。外部送信0回。署名内の対象runや主体の変更を受理しない | Infrastructure/Presentation |
| B11 | 未認証、期限切れ認証、Origin不正、CSRF欠落 | 既存認証契約の401/403。外部送信0回 | Presentation |
| B12 | rating不正、token欠落、空token | 422、外部送信0回 | Presentation |
| B13 | SDKの通信失敗・タイムアウト・認証設定エラー | 503/504として扱い、200を返さない。秘密情報やSDKの生例外を公開しない | Infrastructure/Presentation |
| B14 | 保存成功後にHTTP応答喪失を模擬して再送 | 再送で重複を作らず、200で保存を確認できる | 結合 |
| B15 | SDK応答を保留中に別の軽量リクエストを実行 | イベントループが塞がらない。時間の固定sleepに依存せず同期点で観測する | Infrastructure結合 |
| B16 | 起動・終了、未設定起動 | クライアントの所有者が終了処理を行う。リクエストごとに未終了クライアントを増やさない | Composition |
| B17 | trace内のrunとrootが異なるケース | 表示した最終回答を記録したrunへ紐づき、検索準備だけのrunへ評価しない | Presentation/Infrastructure |
| B18 | 既存の回答・根拠・notice・Jev・会話履歴 | token追加以外の公開データと生成入力を維持する | 回帰 |

冪等性は安定IDを渡したというモック検証だけで証明しない。ロックされたLangSmith SDKの作成・更新契約を確認し、重複ID・作成後更新・応答喪失の動作を模したアダプターテストと実サービス検証を分ける。トレースの遅延到着時も成功を偽らず再試行可能とする。

## 実LangSmithでの受入確認

専用のテスト接続先と明示的なテスト回答を使う。原本や実ユーザーの会話を検証用に送信しない。キーを出力・コミットしない。

1. RESTとWebSocketで各1回答を完了し、回答本文と対象runの対応を確認する。
2. up送信後にLangSmithからfeedbackを読み、key・score・対象run・件数を確認する。
3. 同じupの再送、downへの変更後も同じfeedback IDで1件であることを確認する。
4. テスト環境の2クライアントで同一tokenを同時送信し、重複がないことを確認する。
5. SDKが成功応答を返した後の反映待ちは上限付きpollで扱う。確認不能なら未確認と報告する。

実サービスへの通信は外部API検証として個別に実施し、通常テストの一部として暗黙に実行しない。キー不足は未実施として記録する。
