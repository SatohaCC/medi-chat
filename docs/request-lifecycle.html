Architecture Overview

1. 全体構造とアーキテクチャ境界

medi-chat のバックエンドは「医薬品情報意思決定支援」を単一ドメインとし、クリーンアーキテクチャ / DDD の原則に従って厳格に層分離されています。レイヤー間の依存方向は Presentation → Application → Domain ← Infrastructure となっており、AST静的解析と Import Linter（24契約）によって機械的に制約されています。

Presentation 層

対話配信・API境界

FastAPI Router、Pydantic 公開DTO、WebSocket接続管理、DTO変換アダプター（AppChatService）

Application 層

ユースケース協調

チャット回答調整（chat）、医薬品照合（medicine）、根拠検索統括（retrieval）、プロンプト生成

Domain 層

純粋な業務規則

添付文書モデル（attachment）、YJコード/医薬品マスター（medicine）、不変Primitive・Value Object

Infrastructure 層

技術アダプター

PostgreSQL MVCCランタイム、Janome形態素解析、Jev SDK分類、OpenAI/Gemini LLM SDK

Execution Flow

2. 処理フロー（REST API vs WebSocket ストリーミング）

medi-chat には2つの回答経路があります。用途に応じてタブを切り替えて処理順序を確認してください。

WebSocket ストリーミング処理シーケンス

クライアントがWebSocketでメッセージを送信してから、3つの検出器が順不同で完了し、中間のローカル根拠を先行プッシュしたのち、LLMのトークンが逐次返却されるまでの全行程です。

1

stream_chat_response() Presentation

リクエスト受信 & 接続検証: WebSocket接続（/api/ws または /ws/chat）をハンドシェイク。WebSocketChatRequest によるPydanticスキーマ検証（メッセージ数、YJコード件数1〜50、provider/modelのホワイトリスト検証）を実施。

2

AppChatService.prepare_reply() Presentation

DTO変換 & 先行通知コールバック設定: API型 ChatMessage を Application型 ChatMessage にマッピングし、中間の検索根拠を即座にWebSocketへ送信する publish_logic コールバックを構築して下位層へ渡す。

3

PostgresGenerationRuntime.acquire() Infrastructure

一貫性スナップショットの獲得: PostgreSQLの REPEATABLE READ トランザクションを開始し、公開ポインタ（世代ID）を固定。検索終了まで同一世代の医薬品カタログと添付文書インデックスを確実に参照する。

4

MedicineCatalog.match_yj_codes() Medicine

対象医薬品の解決: 渡されたYJコード群から登録済み製品を検索。同一成分グループごとに集約した ResolvedMedicine を生成。未登録コードがある場合は注意喚起文（notices）を準備。

5

collect_search_criteria() Retrieval

3並行検出器の実行 & 先行配信: Jev（外部意図分類）、Janome（形態素解析）、固定キーワードの3タスクを asyncio.create_task で同時起動。常時取得項目（警告・禁忌等）と、先に完了したローカル検出の根拠を {"type": "sources"} で画面に即時プッシュ。

6

_search_evidence() & merge_evidence() Retrieval

全検出完了後の最終根拠統合: 3検出器すべての条件が出揃った後、PostgreSQLトリグラム検索/BM25インデックスから全根拠を取得。検索単位ID（unit_id）で重複排除し、添付文書の項目番号順（1..24）にソートして確定根拠をWebSocketへ通知。

7

build_answer_messages() Chat

グラウンディング・プロンプトの組み立て: 確定した根拠スニペット（出典URL、改訂年月、見出し番号、本文）と厳格な回答ルール（推測回答の禁止、項目名の明記など）を埋め込んだシステムプロンプトを動的生成。

8

stream_answer() & closing_stream() Chat / Infra

LLMストリーミング生成 & 逐次トークン返却: LLM Provider（OpenAI / Gemini）のストリーミング呼び出しを行い、受信トークンごとに {"type": "text_delta", "content": chunk} を送信。完了時に {"type": "text_done"} を送信。クライアント切断時は closing_stream がジェネレータを確実にクローズ。

REST API 同期処理シーケンス（POST /api/chat）

中間のイベント配信は行わず、全ての検索とLLM文章生成が完全に終了した後に、回答全文と根拠一覧を含む ChatResponse JSON を一括返却します。

1

create_chat_response() Presentation

POST /api/chat に届いた ChatRequest を FastAPI が受け取り、メッセージ非空チェック等のバリデーションを実施。依存性注入（get_chat_service）経由で AppChatService を取得。

2

AppChatService.answer_question() Presentation

環境変数デフォルト（provider/model）を補完し、DTOを内部型へ変換して ChatApplicationService.answer_question() を呼び出す。

3

app_answer_question() Chat

まず prepare_reply() を実行して医薬品照合と3検出器による根拠検索を完了。対象医薬品が未解決で確認が必要な場合（needs_clarification=True）はLLMを一切呼ばずに案内文を即時返却。

4

build_answer_messages() & LLM全文章結合 Chat

プロンプトを構築し、Providerのストリームを "".join([chunk async for chunk in ...]) で一括集約して回答テキストを生成。

5

chat_response_to_api() Presentation

内部の ChatResponse を公開用Pydantic DTO ChatResponse にマッピングし、HTTP 200 JSON としてクライアントへ返却。

Core Engine

3. 3並行検出パイプラインと先行配信（Speculative Streaming）

medi-chat の高速な体感応答を支えているのが、application/retrieval/retrieve_evidence.py 内の並行検出アーキテクチャです。ユーザーの質問意図を解釈するために、特性の異なる3つの処理を同時に走らせます。

⚡ asyncio.create_task による同時起動タスク
① Jev 意図分類器

detect_jev_criteria
Jev SDK / LLM分類モデルを呼び出し、医療対話特有の意図（効能効果、用法用量、副作用、禁忌など）と確率スコアを判定。適合項目番号（section_codes）を導出。

② Janome 形態素解析

detect_morphology_criteria
スレッドプール（asyncio.to_thread）で実行。質問文から対象薬剤名を除外した上で、症状やキーワード（名詞・動詞原形等）を抽出して全文検索条件を作成。

③ 固定キーワード判定

_detect_fixed_keyword_criteria
スレッドプールで実行。「妊婦」「授乳」「運転」「小児」「腎機能」などの医療特有の高頻度フレーズを正規化マッチし、特定添付文書項目（例: 9.5 妊婦）のコードを即座に付与。

常時取得項目（Always-retrieved Sections）と累積配信

医薬品の安全性上極めて重要な 1. 警告 (Warning)、2. 禁忌 (Contraindications)、8. 重要な基本的注意 (Important Precautions) は、質問の文言によらず常時取得条件（ALWAYS）として自動登録されます。

先行配信の仕組み: asyncio.as_completed(tasks) ループにより、Jevの外部通信が完了するのを待たず、軽量なローカル検出器（固定キーワード・形態素解析）が終わり次第、その時点での累積根拠が on_logic_criteria コールバックを通じて WebSocket クライアントへ送信されます。これにより、ユーザーはLLMの生成開始前から引用根拠のカードを画面で確認できます。

Concrete Scenario

5. 実データ・シナリオウォークスルー

具体的なリクエスト例を用いて、各関数の間でデータがどのように変換・受け渡されていくかを追跡します。

【シナリオ】
• 対象薬剤: レクサプロ錠10mg (YJコード: 1179054F1023)
• 質問本文: "レクサプロと併用してはいけない薬（併用禁忌）は何ですか？"
A

入力受信と形式検証

stream_chat_response が {"product_yj_codes": ["1179054F1023"], "messages": [{"role": "user", "content": "..."}]} を受信。 parse_yj_codes が YjCode("1179054F1023") へ変換。

B

医薬品解決と除外語導出

MedicineCatalog.match_yj_codes がデータベースから一般名「エスシタロプラムシュウ酸塩」、販売名「レクサプロ錠10mg」、文書ID「1179054F1023_01」を特定。
除外語リストとして ["レクサプロ錠10mg", "レクサプロ", "エスシタロプラムシュウ酸塩"] が導出される。

C

3並行検出器の判定

• Jev分類器: 意図「相互作用（併用禁忌）」スコア 0.94 → 項目番号 ["10.1"] (併用禁忌)
• 固定キーワード: 「併用禁忌」にマッチ → 項目番号 ["10.1"]
• 形態素解析: 薬剤名を除外した「併用 薬」からキーワード ["相互作用", "併用"] を抽出。
• 常時取得: 項目 ["1", "2", "8"]（警告・禁忌・基本的注意）を自動付加。

D

根拠の取得と統合（merge_evidence）

PostgresEvidenceReader が該当添付文書から「10.1 併用禁忌」の表データを取得（MAO阻害剤: セレギリン塩酸塩、ラサギリンメシル酸塩等）。 merge_evidence が項目番号順（2. 禁忌 → 10.1 併用禁忌）にソートして重複排除。

E

プロンプト注入とLLM生成

build_answer_system_prompt が「10.1 併用禁忌」のセレギリン塩酸塩（エフピー）等の記載を埋め込み、「推測せず表の記載通りに回答せよ」というルールをLLMに指示。 OpenAI/Gemini が「レクサプロの併用禁忌として、MAO阻害剤（セレギリン塩酸塩等）が指定されています（項目 10.1 参照）...」という文章をストリーミング返却。

Design Principles

6. 設計の勘所と防御機構まとめ

設計課題 採用したアーキテクチャ もたらされるメリット
外部LLMや通信の遅延 3並行検出器 + 先行配信（Speculative Streaming） JevやLLMを待たずに、手元のローカル辞書・形態素解析で判明した根拠を先行プッシュ。体感レスポンスを劇的に向上。
データ更新中の読取不整合 PostgreSQL MVCC REPEATABLE READ + 公開世代ポインタ バックグラウンドで新XMLが取り込まれても、質問処理中は最初に固定した同一世代スナップショットを一貫して読み取る。
クライアント中断時のリソース浪費 closing_stream + 非同期ジェネレータクローズ ユーザーがタブを閉じた瞬間に、LLM API呼び出しや待機タスクを aclose() で即時中断。無駄な課金とソケット枯渇を防止。
レイヤー破壊・DTO逆変換のバグ Import Linter 24契約 + AST境界検査 ルーターがDBを直読みしたり、出力用DTOを内部モデルに復元するような保守困難な依存関係をコミット前に機械的に遮断。
LLMのハルシネーション（幻覚） 厳格なグラウンディングプロンプト + 未登録時の回答停止 対象医薬品が不明な場合はLLMを一切呼ばずに即案内を返却。取得根拠の項目番号・出典URL・改訂年月の明記をプロンプトで強制。
