## 本文を読むトリガー条件

WebSocket等のイベント回数・配信順序を変更する作業、または非同期処理の途中結果を累積配信する作業。

## 適用する条件／適用しない条件

公開イベントを複数のテスト・利用側が検証している場合、または累積配信の各段階でIOを伴う場合に適用する。文言だけの変更や、IOを伴わない静的表示だけの変更には検索回数の検証を要求しない。

## 観察した失敗と証拠

PR #4の初期実装では新規の段階配信テストを追加したが、既存の `test_tc134_fixed_end_ping_then_normal_same_connection` は `sources` が1回だけ届く期待のままだった。また、ローカル条件が2件ある場合に固定→固定＋形態素→固定＋形態素＋Jevを再検索し、3条件に対して6回の検索を行う構造になっていた。

## 原因

- 確認できた原因: 初期検証対象に既存の公開契約テストが含まれていなかった。累積通知で全条件を再検索しており、検索回数の受入条件がなかった。
- 未確認の仮説: 実環境での遅延への寄与は未計測。

## 次回の具体的な確認手順

イベントの生成側だけでなく、イベント名・順序・回数を参照する既存テストと利用側を検索する。途中結果と最終結果の内容・取得元・順序を確認する。IOを伴う累積配信では条件別の実行回数を測り、完了済み処理が再実行されないことを検証する。

## 対策の検証

- [公開契約テスト](../../../backend/tests/test_product_identity_public.py)で先行・統合の両スナップショットと同接続次要求を検証する。
- [段階配信テスト](../../../backend/tests/test_progressive_retrieval.py)で3条件が各1回だけ検索され、新しい要求では再検索されることを確認する。
- レビュー対応差分で公開契約・段階配信・製品同定・REST/WS・世代管理・依存方向のpytest 153件成功。要求間の再検索を追加確認後、段階配信11件を再実行して成功。型検査、変更ファイルのRuff lint/format、差分確認も成功。backend全体のテストではない。
- 外部Jev・回答LLMはテストダブル。実通信・ブラウザ・実環境の表示時間は未検証。
