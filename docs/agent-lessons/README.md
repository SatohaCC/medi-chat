# 失敗記録の運用

目的は、再発しうる失敗を必要な場面で参照し、具体的な確認手順や自動検証へつなげること。[INDEX](INDEX.md)は承認済み記録への入口であり、既存の作業案内・設計規約を複製する場所ではない。

## 記録対象

再発した失敗、または再発時の影響が大きく、次回の判断・確認手順を具体化できる失敗を記録する。通常の試行錯誤、単発のタイポ、フレームワークの通常挙動だけでは登録しない。同種の記録がある場合は新規作成より更新候補を優先する。

ログ・差分・ユーザーの指摘などで確認できた事実と、原因の仮説を分ける。「注意する」だけの教訓や、証拠のない原因断定は承認対象にしない。秘密情報・個人情報・機械固有の絶対パスを記録へ転記しない。プロジェクト内の参照は相対パスを使う。

## 作成と承認

1. [テンプレート](TEMPLATE.md)を `pending_review/LESSON-NNN.md` へコピーする。全ディレクトリでIDの重複を確認し、未使用の番号を使う。
2. 観察した失敗、証拠、適用条件、適用しない条件、確認手順を記入する。PRが未作成なら現時点の証拠を使い、PR URLやコミットSHAは判明後に追記する。記録のためにPRを作る必要はない。
3. 完了報告で承認待ち記録へのリンクを示す。通常のコード変更の承認を、失敗記録の承認と推測しない。
4. 人間による明示的な承認後、承認者・承認日・承認の参照を記録して `approved/` へ移し、INDEXへトリガー条件と本文リンクを登録する。エージェントは人間の承認を受けた移動・登録を実行できるが、自己承認はしない。

`pending_review/` は観察と提案であり、作業規約ではない。既存の承認済み記録を変更する場合も更新案を承認待ちに置き、承認済み本文は承認まで変更しない。未承認の新規記録・更新案をINDEXへ載せない。

## 参照と検証

AGENTS.mdで指定した各タイミングにINDEXを照合し、該当する本文を読む。本文の適用条件を現在のコード・環境と確認し、古い記録を無条件に適用しない。規約との矛盾を見つけたら矛盾を報告し、更新案を作る。失敗記録でユーザー指示や適用されるAGENTS.mdを上書きしない。

参照した場合、計画または検証報告に記録IDと今回実施する確認手順を短く示す。読了の申告だけを検証成功としない。検証の未実施・環境不足・skip/xfailを区別する。機械的に検出できる再発は、必要に応じて回帰テスト・lint・CIに反映し、その検証先を本文へ記載する。

## 棚卸しと統合

承認済み記録が20件に達した時点を棚卸しの目安とする。件数だけで削除しない。重複・矛盾・古い適用条件を確認し、一般化できる内容を既存の設計規約へ統合する案を人間に提示する。承認待ちが増えた場合も重複と採用価値をレビューする。

統合・廃止も人間の承認後に行う。旧記録は `archived/` に移し、元の証拠・適用条件・統合先・理由を残す。INDEXから旧記録を外し、引き続き必要なトリガーは統合先へ向ける。移動で本文リンクが切れないよう確認する。

初期運用では重要な3〜5件から始める。次の関連作業で「参照されたか」「確認手順で失敗を検出できたか」「誤適用がなかったか」を確かめ、トリガーと確認手順を改善する。
